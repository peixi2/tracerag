# TraceRAG AI 全栈面试问答

## 一分钟介绍

“TraceRAG 是我从零实现并部署到公网的企业知识助手。我把重点放在三个工程问题：答案依据是否可核对、模型不可用时能否降级、检索改动后如何发现质量回归。系统用中英文分词和 BM25 召回 Top 4 证据，回答同时返回来源、置信度、traceId 和阶段耗时；DeepSeek 超时或未配置时，用相同证据生成确定性摘要。固定评测集计算 Recall@4 和 MRR，分别定位召回覆盖和排序质量。当前真实实现是 BM25，我不会把向量库或 reranker 写成已上线能力。”

## 高频问题

### 这是真 RAG 吗？

它实现了检索增强生成的完整数据流与返回契约。当前检索是 BM25，不是 embedding；这使免费演示可解释、稳定且无需向量服务。生产可替换为混合检索而不改变前端接口。

### 为什么选择 BM25，不直接使用向量数据库？

当前语料主要是错误码、产品规则和操作说明，精确术语区分度高，数据集也很小。BM25 的成本低、结果稳定、分数来源可解释，适合先验证链路和评测方法。向量检索更擅长同义改写和语义匹配，但会引入 embedding 模型、向量索引和额外评测变量；我会在固定集上证明混合召回有收益后再引入。

### 中文分词为什么使用单字和双字词？

按空格切中文几乎无法检索，单字和相邻双字词能以很小实现成本覆盖“重复消费”“登录异常”等短语，同时避免依赖外部分词服务。缺点是 token 数量增加，也无法理解同义词和完整词边界，所以它是当前小规模场景的可解释基线，不是通用中文检索方案。

### BM25 比关键词计数多解决了什么？

IDF 提高稀有词的区分度，词频饱和避免重复出现同一词无限抬高分数，文档长度归一化避免长文档仅凭词多占优。项目使用 `k1=1.2`、`b=0.75` 的常见参数形式，并把 Top 4 最高分归一化为前端可比较的相关度。

### 怎么降低幻觉？

限制回答只能使用检索证据，返回来源编号，低证据时拒答，记录 traceId，并用离线评测监控召回。提示词只是最后一层，检索质量和输出校验同样重要。

### 引用来源是否就能证明答案正确？

不能。返回来源只能让答案可核对，模型仍可能错误解释证据。当前 `citationCoverage` 只反映回答是否绑定来源，不是逐句事实一致性。生产版本应增加引用编号解析、句子与证据的蕴含校验、人工标注集和低置信度拒答。

### 为什么需要 fallback？

模型 API 可能超时、限流或余额不足。核心知识查询不能因此不可用，因此设置超时，并使用相同证据生成确定性摘要，同时向用户展示真实运行模式。

### fallback 会不会掩盖模型故障？

不会静默掩盖。响应明确返回 `GROUNDED_FALLBACK`，trace 也记录生成模式和耗时。当前演示还缺少指标告警；生产环境应统计模式占比、模型错误码和连续降级时间，超过阈值时告警。

### 为什么关注 Recall@4 和 MRR？

生成之前必须先找到正确证据。Recall@4 衡量是否召回，MRR 进一步衡量正确文档是否排在前面，两者比只看回答是否流畅更能定位检索问题。

### 为什么不直接评测最终答案？

最终答案同时受召回、排序、Prompt 和模型波动影响，只看一个总分很难定位问题。先用 Recall@4 和 MRR 固定检索基线，再单独评估引用正确性和答案忠实度，出现回归时才能知道该改检索还是生成。当前六条用例只能作为回归烟雾测试，不能代表生产质量。

### 置信度是模型正确率吗？

不是。当前置信度是前两条归一化检索分数的平均值，用来表达“证据匹配强弱”，没有经过概率校准。真实系统需要在标注集上分析分数分布，确定拒答阈值，并分别处理有答案和无答案问题。

### traceId 有什么实际用途？

它把用户看到的回答与查询模式、来源数量、总耗时和数据库记录关联起来。接口还返回 rewrite、retrieve/rank、generate 三阶段耗时，因此回答异常时可以先区分是没有召回、排序不对、模型失败还是单纯延迟升高。

### 如何升级为生产级系统？

先补齐租户级文档权限、数据同步、语义分块和更大的标注评测集，再用指标比较 BM25、embedding 与混合召回。确认收益后增加 reranker，并补充 Prompt/模型版本、敏感信息过滤、在线反馈、异步评测和告警。权限过滤必须发生在生成前，不能只在前端隐藏来源。
