# TraceRAG

TraceRAG 是一个可溯源企业知识助手，目标不是把大模型 API 包装成聊天框，而是回答三个工程问题：答案依据能否被核对，外部模型不可用时服务能否继续工作，检索质量下降时团队能否用指标发现原因。

系统把查询标准化、BM25 召回排序、受证据约束生成、来源引用、阶段 trace 和固定评测集串成一个可观察闭环。当前版本刻意使用可解释、低成本的 BM25，而不是把尚未部署的 embedding、向量库和 reranker 写进技术栈。

- 在线演示：https://tracerag-demo.onrender.com
- 演示账号：`admin` / `admin123`
- 技术栈：Python 3.12、FastAPI、SQLAlchemy、MySQL、Vue 3、BM25、DeepSeek 兼容接口、Docker、Render

## 核心问题与设计

| 工程问题 | 当前设计 | 可观察结果 |
| --- | --- | --- |
| 中文短查询直接按空格切分会丢失词语关系 | 保留英文 token，并生成中文单字与相邻双字词 | “重复消费”“登录异常”等词可参与匹配 |
| 只看关键词命中会偏向长文档 | BM25 同时使用 IDF、词频饱和和文档长度归一化 | Top 4 按相关性排序并返回归一化得分 |
| 流畅回答可能没有知识依据 | 模型只接收召回证据，关键结论要求引用资料编号 | UI 同屏展示回答、来源、得分与置信度 |
| 模型超时、限流或未配置 | 使用同一组证据生成确定性 `GROUNDED_FALLBACK` | 返回真实模式，核心查询链路仍可演示 |
| 回答错误时无法定位阶段 | 记录 rewrite、retrieve/rank、generate 三阶段耗时 | 每次查询返回 `traceId` 并持久化摘要 |
| 检索改动后质量退化不可见 | 固定问题集计算 Recall@4 和 MRR | 评测结果写入 MySQL，可比较历史运行 |

## 查询链路

问题先压缩多余空白，再分解为英文 token、中文单字和双字词。检索器针对已发布知识文档与支持工单计算 BM25：稀有词由 IDF 获得更高权重，高频词通过饱和项限制影响，文档长度归一化避免长文本仅凭词多占优。系统选取最多 4 条证据，并按最高分归一化相关度。

有 DeepSeek 凭据且存在证据时，模型收到问题与证据片段，系统提示要求关键结论引用资料编号；未配置、连接失败、18 秒超时、限流或响应异常时，系统切换到确定性摘要。无证据时直接拒答，不让模型脱离知识库自由发挥。回答最终携带来源、置信度、运行模式、`traceId`、总耗时和三阶段轨迹。

## 可验证证据

- 内置 12 篇知识文档、8 条支持工单和 6 条固定评测用例；用户新增文档、查询轨迹和评测历史都写入云 MySQL。
- 单元测试验证中文双字词、相关文档排首位、fallback 绑定来源和云数据库 URL 转换。
- 固定评测分别计算 Recall@4 与 MRR：前者判断正确文档是否进入候选集，后者判断它是否排得足够靠前。
- 多阶段 Docker 构建将 Vue 产物放入 FastAPI 静态目录，Render 只运行一个 Web Service。
- TiDB Cloud 使用独立 `tracerag` schema，并通过 TLS 校验服务端主机。

## 已实现与未实现

当前检索是 BM25，没有 embedding、向量数据库、cross-encoder reranker 或 SSE。`citationCoverage` 当前验证回答是否绑定检索来源，不等价于逐句事实一致性。生产化还需要文档切块、租户级权限过滤、提示词和模型版本、敏感信息处理、在线反馈及更严格的引用校验；这些是演进方向，不是当前已上线能力。
